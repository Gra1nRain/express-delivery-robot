## 根因判断

这是有实车与 bag 证据支持的判断：

1. 控制器把最多 `2.0 s` 的延迟位姿用底盘速度外推到当前时刻。
2. 当一次 TF 延迟达到约 `2.03 s` 时，外推超过上限并被禁用。
3. 新观测恢复为原始雷达时间戳，而上一条已接受观测的时间戳曾被外推到
   当前时刻，所以状态估计器同时检测到陈旧位姿和相对上一状态的时间倒退。
4. 安全链按设计停车。

原始 TF 并没有倒序，因此放宽状态连续性判断或忽略安全停止都不是正确修复。

## 第一版修复及否决证据

第一版曾在 Livox 驱动与 FAST-LIO 之间加入 Python 消息适配节点。它在
电脑端通过了纯逻辑测试，但第二次现场启动暴露出不可接受的运行时开销：

- 运行标签：`day5_full_route_livox_rebased_139c3de_20260724_123450`；
- 适配器测得固定偏移 `+1.277149 s`；
- 转发器没有进入运行态，`relay_active=false`，里程计位移为零；
- 大体积 Livox `CustomMsg` 经 Python 反序列化、修改和再序列化后持续积压；
- 约两分钟后 `/cloud_registered_body` 消息时间落后主机约 `25 s`；
- 局部规划为 `COSTMAP_TF_UNAVAILABLE`，近障节点为 `stale_cloud`，因此
  `local_ready_gate` 超时拒绝启动。

所以 Python 数据面适配方案已被现场证据否决并从代码中移除。

## 当前修复方案

项目保存对官方 Livox ROS 2 驱动的最小补丁，并只在 Day 5 launch 中设置
`LIVOX_ROS_FORCE_HOST_TIMESTAMP=1`：

- 驱动在接收每个激光或 IMU UDP 包时直接使用官方代码已有的主机
  `high_resolution_clock` 分支；
- 同时把发布调度切换到官方“无外部时间同步”分支；
- 不再复制或重新序列化点云，保持官方 C++ 数据路径性能；
- Day 1 默认不设置该环境变量，维持原始驱动行为。

### 根因判断

这是由实车 bag、规划轨迹和控制器实现共同支持的判断：

1. 全段参考轨迹相邻点约 `0.10 m`，当前速度下相邻参考时刻约
   `0.50–0.67 s`。
2. MPPI 每 `0.05 s` 预测一次，但旧实现用 `searchsorted` 直接选取
   下一个完整路点。进入急弯时，第一拍会提前采用下一点的完整曲率，整个
   rollout 也跟踪阶梯状参考。
3. 在实车对应的急弯索引 `91–98`，连续时间插值后的第一拍曲率通常仅比
   当前点前进约 `10%`；旧实现却直接跳到下一点。比如索引 `91` 的旧参考
   为 `0.154323 1/m`，插值后为 `0.015432 1/m`。
4. 曲率相位提前使车辆切入弯道内侧；原安全策略在误差刚超过 `0.15 m`
   时立即输出零速，形成“有可恢复误差但不允许运动恢复”的锁死状态。

### 当前软件修复与离线验证

- MPPI 的整段预测参考改为按每个控制时刻连续插值位置、航向、速度和曲率，
  不再选择稀疏路点形成阶梯参考。
- MPPI 不再以自己的固定跟踪误差阈值抢先返回零指令；它持续提供可纠偏命令，
  跟踪误差的限速、滞回和最终停止统一由独立安全监督器裁决。
- 跟踪误差改为分级策略：
  - 横向误差超过 `0.10 m` 或航向误差超过 `10°` 时进入恢复态，以
    `0.06 m/s` 上限继续纠偏；
  - 回落到 `0.06 m` 且 `5°` 以内才退出恢复态，避免阈值附近抖动；
  - 只有横向误差超过 `0.40 m` 或航向误差超过 `45°` 并持续 `1.0 s`
    才进入 `SAFE_HOLD`。
- 急停、底盘故障、状态失联、控制命令失联和障碍物停止仍是即时硬保护。
- 电脑端完整测试：`95 passed`。
- 全段纯离线闭环仿真：
